# 02 — User journeys

Each journey below was walked end-to-end against a real cluster
(`hack/ui-lima-demo.sh`, kind cluster `landlock-genprof-core`) during this
convergence pass, not simulated. Observation ID, namespace, and fact counts
in "Journey A" are from an actual captured run.

## Journey A — Platform engineer: first observation to proposal

1. **Open the console.** Environment panel shows Cluster
   `kind-landlock-genprof-core`; Identity and Namespace resolve from the
   bound session (see [15-known-limitations.md](15-known-limitations.md) for
   a first-load edge case that was fixed in this pass).
2. **Workloads.** Table lists discovered Deployments/pods/containers in the
   bound namespace. Operator clicks **Inspect** on
   `landlock-genprof-demo-workload / nginx`.
3. **Observations.** The lifecycle control shows "No observations yet for
   this workload." and a single enabled primary action, **Start
   observation**.
4. Operator clicks it. The status line moves through "Attaching evidence
   capture…" → "Observing runtime activity…" while workload activity
   happens. **Stop observation** becomes the visible secondary action;
   **Start observation** is disabled (only one active observation per
   workload at a time is meaningful — see
   [05-observation-state-model.md](05-observation-state-model.md)).
5. Observation completes on its own (or via **Stop observation**). Status
   line reads "Latest observation: completed." An observation card appears
   under **Observation records**: `landlock-genprof-demo-workload · Completed
   · 6 capability facts`.
6. Operator clicks **Review evidence** (primary, because the observation is
   `COMPLETED`). Evidence panel shows the 6 capability facts
   (`CAP_CHOWN`, `CAP_DAC_OVERRIDE`, `CAP_SETGID`, `CAP_SETPCAP`,
   `CAP_SETUID`, `CAP_SYS_ADMIN`) and — in the real captured run — an
   **Evidence state unknown** badge, because the backend's qualification
   proof conditions were not all satisfied even though facts exist. See
   [06-evidence-model.md](06-evidence-model.md); this is the fail-closed
   behavior working as intended, not a bug in the walkthrough.
7. Operator clicks **Generate proposal** (enabled because the observation is
   `COMPLETED`, independent of evidence quality — generation attempts
   server-side and returns a clear `NO_CANDIDATE` error via the shared error
   banner if the backend actually refuses it).
8. Operator navigates to **Proposals & Governance** and sees the generated
   proposal with `reviewedBy`/`approvedBy`/`rejectedBy` attribution,
   candidate digest, and per-action disabled reasons.

## Journey B — Security reviewer: review, approve, handle a stale conflict

1. Reviewer opens **Proposals & Governance**, finds a `Draft` proposal
   generated by a platform engineer's observation.
2. Clicks **Review** → proposal moves to `Reviewed`; `reviewedBy` is set
   server-side from the authenticated identity, not client input.
3. A second browser tab (or a slow reviewer) attempts **Approve** using a
   `resourceVersion` that is no longer current. The server returns `409`;
   the UI does not silently retry. It shows: *"State changed since this
   decision was loaded. The previous decision was not applied. Refresh and
   decide again against the current state."* with an explicit **Refresh**
   button. See [12-security-ux-constraints.md](12-security-ux-constraints.md).
4. Reviewer refreshes, re-reads the current `resourceVersion` and
   `candidateDigest`, and approves against current state. `currentAuthority`
   becomes `VALID`.
5. If the reviewer's capability set does not include `proposal.apply` (a
   real, common case — see the captured screenshot in
   [screenshots/README.md](screenshots/README.md)), **Apply** renders
   disabled with `NOT_AUTHORIZED — capability is unavailable.` The reviewer
   is never told the button doesn't exist; they're told why it's unusable
   for them.

## Journey C — Restricted user: explicit namespace, no list access

1. Identity is opened whose SSAR checks fail `list namespaces`.
   `discovery.mode === "EXPLICIT_ONLY"` is returned by
   `/api/v09/environments/{session}/namespaces`.
2. The Namespace `<select>` is hidden; a labeled text input and **Open**
   button take its place, with inline help: *"Namespace discovery is not
   permitted for this identity. Enter a namespace you are authorized to
   access."*
3. User enters a namespace they know they have access to and clicks
   **Open**. If they are in fact authorized, the session binds exactly as
   for a discovered namespace — same Workloads/Observations/Proposals
   surfaces, same capability gating. If they are not authorized, the read
   fails with the same `UNAVAILABLE`/error treatment as any other
   authorization failure — no distinct "you don't exist" leakage path.

## Journey D — Evidence UNKNOWN, explicitly not proposal-ready

This is the scenario called out directly in the mission brief
(`Execution: NOT_AVAILABLE`, `Frozen: true`, `evidence UNKNOWN`). The
current implementation's `renderObservation`/`renderEvidenceSource`
functions were built around exactly this distinction:

- `COMPLETED`/`Frozen: true` is shown as **Observation finalized** — a
  statement about the observation lifecycle only.
- Each evidence source shows its own `AVAILABLE` / `EMPTY` / `UNKNOWN`
  badge and a plain-language explanation (`evidenceExplanation` in
  `workbench_ui.go`), independent of the observation's own completion
  state.
- `UNKNOWN` renders with the same neutral/warning treatment as any other
  non-success state (`.unknown` CSS class — grey/muted, never
  `.success`/green). See [06-evidence-model.md](06-evidence-model.md).
